# 二期开发待办：通用 Android Live Photo / Motion Photo 清理

当前发布版本：`v0.1.0`

v0.1 已完成 vivo 传统双文件 Live Photo 管理能力：

```text
IMG_001.jpg
IMG_001.mp4
```

二期目标是在现有 Android 项目基础上继续开发，不推倒重写，把 LiveKit 从“vivo 双文件清理器”升级为“通用 Android Motion Photo 清理器”。核心仍然是：扫描 Android 图库，找到 Live Photo，统计动态视频占用，安全移除动态部分，保留静态原图。

## 1. 背景和目标

很多新 Android 设备不再使用“JPG + 独立 MP4”，而是使用单文件 Motion Photo：

```text
一个 JPG / HEIC / AVIF
=
静态照片
+
Motion Photo metadata
+
内嵌视频
```

因此不能继续只靠“同目录是否存在同名 MP4”判断 Live Photo。

二期目标：

```text
vivo Legacy 双文件
+
Android 官方 Motion Photo 1.0
+
未来逐步扩展 OEM 私有格式
```

## 2. 第一依据：Android 官方 Motion Photo 1.0

标准 Motion Photo 结构：

```text
Primary Image
+
可选辅助资源
+
Motion Video
```

主图支持：

- JPEG
- HEIC
- AVIF

核心 XMP 信息包括：

```text
Camera:MotionPhoto
Camera:MotionPhotoVersion
Camera:MotionPhotoPresentationTimestampUs

Container:Directory

Item:Semantic
Item:Mime
Item:Length
Item:Padding
```

其中：

```text
Semantic = Primary       静态主图
Semantic = MotionPhoto   动态视频
```

标准规定 Motion Photo 视频位于文件最后，因此可以通过 metadata 得到：

```text
videoStartPosition
videoSize
photoStartPosition
photoSize
photoPresentationTimestampUs
```

这些字段用于计算动态视频大小和可释放空间。

## 3. 优先使用 Android Media3

不要一开始从零实现完整 Motion Photo parser。

优先研究和封装 Media3：

```text
MotionPhotoMetadata
photoStartPosition
photoSize
videoStartPosition
videoSize
photoPresentationTimestampUs
```

建议封装：

```text
Media3MotionPhotoAdapter
```

业务层不要直接依赖 Media3 的具体实现。后续如果 Media3 对某些 OEM 样本解析不足，可以在 adapter 外补 detector。

## 4. 安全识别规则

不能只判断：

```text
MotionPhoto = 1
```

因为图片被编辑后可能残留 metadata，但视频实际已经不存在。

必须验证：

```text
Motion metadata
+
Container item
+
video offset
+
video size
+
真实视频 payload
```

另外不能简单从 JPEG 的 `FF D9` 后全部删除。Ultra HDR Motion Photo 可能是：

```text
Primary
GainMap
MotionPhoto
```

如果从 JPEG 结束位置截断，可能误删 GainMap / HDR 数据。

## 5. 推荐架构

保留当前 vivo 逻辑，但封装为 detector。

```text
LivePhotoDetector
├── VivoLegacyDetector
├── GoogleMotionPhotoDetector
├── HuaweiHonorDetector
├── OppoDetector
├── SamsungDetector
└── FutureDetector
```

不要按品牌写业务判断：

```text
if Xiaomi
if OPPO
if Samsung
```

应该优先根据文件协议判断。同品牌不同系统版本可能使用不同格式，不同品牌也可能复用 Google Motion Photo 协议。

## 6. 统一结果模型

建议原生层新增：

```kotlin
enum class LivePhotoProtocol {
    NONE,
    VIVO_LEGACY_PAIR,
    GOOGLE_MOTION_PHOTO_V2,
    GOOGLE_MICRO_VIDEO_V1,
    HUAWEI_HONOR_MOVING_PHOTO,
    OPPO_ONEPLUS_O_LIVE,
    SAMSUNG_MOTION_PHOTO,
    HEIC_MOTION_PHOTO,
    AVIF_MOTION_PHOTO,
    EMBEDDED_MP4_UNKNOWN,
    UNKNOWN
}

enum class DetectionConfidence {
    NONE,
    WEAK,
    STRONG,
    VERIFIED
}

data class LivePhotoInfo(
    val protocol: LivePhotoProtocol,
    val imageUri: Uri,
    val totalSize: Long,
    val stillSize: Long,
    val motionSize: Long,
    val videoOffset: Long?,
    val videoSize: Long?,
    val confidence: DetectionConfidence,
    val canPlay: Boolean,
    val canExtract: Boolean,
    val canStripSafely: Boolean,
    val reason: String
)
```

只有 `STRONG` 或 `VERIFIED` 才进入主 UI 的 Live 管理能力。`WEAK` 只在 Inspector 展示，不允许清理。

## 7. 三层能力分离

必须分开：

```text
Detector
→ 识别协议、位置和大小

StripEngine
→ 删除动态部分 / 生成静态副本

Validator
→ 验证处理结果是否安全
```

不要把识别、删除、验证混在扫描器里。

## 8. 当前支持顺序

第一阶段：

```text
vivo Legacy
✅ 保留

标准 JPEG Motion Photo
✅ 新增完整检测

HEIC / AVIF
⚠️ 先检测
❌ 暂时不做破坏性修改
```

后续再逐渐增加 OEM 私有格式。

## 9. Detector 规则

### VivoLegacyDetector

检测：

- 同目录
- 同基础文件名
- JPG/JPEG + MP4
- MP4 时长 1 到 5 秒
- 拍摄时间接近
- MP4 可读

能力：

- 可播放
- 可删除 companion MP4
- 可进入应用回收站

### GoogleMotionPhotoDetector

优先基于 Android 官方 Motion Photo 1.0 + Media3。

检测：

- JPEG / HEIC / AVIF 候选
- 存在官方 Motion Photo metadata
- 存在 Container Directory
- 能解析 Primary / MotionPhoto item
- videoStartPosition 合法
- videoSize 合法
- 对应位置存在有效视频 payload

能力：

- JPEG：可提取视频，可生成静态副本
- HEIC / AVIF：先识别，不清理

### GoogleMicroVideoV1Detector

兼容旧格式：

- `GCamera:MicroVideo=1`
- `GCamera:MicroVideoVersion=1`
- `GCamera:MicroVideoOffset`
- offset 合法
- 对应位置存在有效 MP4

注意：新规范中 MicroVideo 字段已经被 Motion Photo V2 替代，但老 Pixel / 老小米样本仍可能存在。

### OEM Detector

后续拿到样本再逐步增加：

- Huawei / Honor Moving Photo
- OPPO / OnePlus O-Live
- Samsung Motion Photo
- vivo 新协议
- Fusion / 其他特殊协议

原则：如果现有 `GoogleMotionPhotoDetector` 可以识别，就不新增品牌 detector。只有标准 detector 无法识别时，才研究 OEM 私有格式。

### EmbeddedMp4FallbackDetector

最后兜底：

- 扫描疑似 MP4 `ftyp` box
- 校验 MP4 box 结构
- 只能作为疑似结果

默认：

```text
canStripSafely = false
```

## 10. 删除 / 清理逻辑

vivo：

```text
JPG + MP4
→ 删除 companion MP4
```

单文件 Motion Photo：

```text
图片 + metadata + Motion Video
```

不能直接粗暴修改原文件。

开发阶段必须：

```text
原文件
→ 生成静态副本
→ Validator
→ 验证通过
→ 才考虑替换原文件
```

禁止：

```text
JPEG
→ Bitmap decode
→ JPEG recompress
```

因为这会重新有损压缩静态照片。

目标是：

```text
保留原始 JPEG 压缩数据
只移除 Motion Video
并正确处理 Motion metadata
```

## 11. Validator 至少检查

处理后必须确认：

- 图片能正常解码
- 分辨率不变
- Orientation 不变
- 关键 EXIF 不意外丢失
- HDR / GainMap 不被误删
- 静态照片没有重新压缩
- Motion Video 确实不存在
- 文件大小正确减小
- 再次扫描时不再被识别为 Live Photo

任何验证失败：

```text
不修改原始照片
```

## 12. 性能策略

全库扫描不能深度解析所有文件。

分层：

1. 轻量扫描
   - 只读 MediaStore 字段
   - 建立 vivo 双文件索引
   - 判断单文件 Motion Photo 候选

2. 候选深度检测
   - 优先通过 Media3 / XMP metadata 获取位置
   - 只读必要 segment / tail range
   - 不整文件读入内存

3. 用户点击后完整验证
   - 详情页或 Inspector 再做完整解析
   - 提取视频、生成静态副本只在用户操作时执行

- 显示 photoSize

## 15. Live Photo Box 参考原则

GitHub 项目 Live Photo Box 已经研究了多个厂商协议。

参考地址：

```text
https://github.com/LengxiQwQ/live-photo-box
```

可重点参考方向：

- Google Micro Video
- Google Motion Photo
- OPPO / OnePlus O-Live
- Huawei / Honor Moving Photo
- Samsung Motion Photo
- vivo 新格式
- Fusion / 特殊协议

最值得参考：

```text
LivePhotoBox.Core
Services / Protocols
```

关注：

- 协议识别
- Motion 视频定位
- 拆分逻辑
- XMP 清理
- JPEG segment 无损重建
- EXIF / ICC / GPS 保留
- vivo pairing
- Huawei / Honor
- OPPO
- Samsung
- vivo 新协议

但 Google 标准 Motion Photo 仍以 Android 官方 Motion Photo 1.0 + Media3 为第一依据。

### GPL-3.0 约束

Live Photo Box 使用 GPL-3.0。

如果 LiveKit 不准备按 GPL-3.0 开源：

```text
不要直接复制代码
```

可以：

- 阅读协议实现
- 学习算法
- 理解 metadata
- 自己重新实现

### GitHub 参考实现使用规则

后续实现 detector / stripper / validator 时，允许查阅 GitHub 上已有 Motion Photo / Live Photo 实现，但必须按下面规则执行：

```text
1. Android 官方 Motion Photo 1.0 和 AndroidX Media3 永远是 Google Motion Photo 的第一依据。
2. GitHub 项目用于补充 OEM 兼容经验、异常样本、边界条件和测试思路。
3. 每次参考第三方实现时，在开发记录或代码注释中记录项目名、链接、license 和参考点。
4. 不直接复制 GPL、未知 license 或 license 不兼容项目的核心代码。
5. 如果某个行为来自第三方项目，需要用自己的测试样本复现并重新实现。
6. 对于 vivo / OPPO / Xiaomi / Samsung 等私有格式，先做只读识别和 Inspector，再做清理写入。
```

当前优先参考维度：

```text
- Live Photo Box: 多协议分类、拆分/合并流程、异常修复思路、测试样本维度
- AndroidX Media3 / ExoPlayer: XMP Motion Photo metadata 解析思路
- Android 官方文档: Motion Photo 1.0 容器结构、XMP 字段、GainMap / Ultra HDR 安全边界
```

## 16. LiveKit 和 Live Photo Box 的目标区别

Live Photo Box 更像：

```text
跨厂商 Live Photo 格式工具箱
→ 识别
→ 拆分
→ 合并
→ 转换
→ 修复
```

LiveKit 的核心产品目标是：

```text
扫描 Android 图库
→ 找到所有 Live Photo
→ 统计动态视频占用
→ 告诉用户可以释放多少空间
→ 批量移除动态部分
→ 保留静态原图
→ 安全验证
```

所以重点放在：

- MediaStore 扫描
- Scoped Storage
- 批量统计
- 删除授权
- 安全替换
- 失败保护
- Validator
- OEM Gallery 兼容
- 用户体验

不要把主要精力放在重复研究所有协议上。

## 17. 当前最合理开发顺序

```text
STEP 1  检查现有代码，保证 vivo V1 正常
STEP 2  封装 VivoLegacyDetector
STEP 3  建立统一 LivePhotoInfo / Detector 架构
STEP 4  增加 Live Photo Inspector
STEP 5  接入 Media3
STEP 6  实现标准 JPEG Motion Photo 检测
STEP 7  自己生成 Motion Photo 测试样本
STEP 8  实现视频提取
STEP 9  实现 Generate Static Copy
STEP 10 实现 Validator
STEP 11 在 vivo + Google Photos 上完成闭环测试
STEP 12 以后拿到 OEM 样本，再参考 Live Photo Box 增加私有协议支持
```

## 核心原则

```text
安全性 > 正确性 > 支持品牌数量
```

未知格式宁可：

```text
DETECT_ONLY / UNSUPPORTED
```

也不要执行危险删除。

LiveKit 的方向不是重新做一个 Live Photo Box，而是利用 Android 官方规范、Media3 和已有开源协议研究，快速补齐格式层，把主要精力放在“Android 手机上安全、批量、无损地删除 Live Photo 视频并释放空间”这件事上。
